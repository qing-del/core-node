# 协同文档 v0.5｜光标、框选高亮提示

> 本文记录协同文档 v0.5 中“远端光标、文本框选高亮、协作 Agent 状态”的后端约定。前端实现章节暂不展开，后续按同一状态模型补充。

## 1. 目标与边界

本阶段为协同文档补充在线状态（Awareness）能力，使同一文档 Room 内的协作者能够看到：

- 远端 Session 的光标位置；
- 远端 Session 的文本框选高亮；
- 光标所属用户和 Session 标识；
- 后续协作 Agent 的阅读、思考、编辑与空闲状态。

Awareness 是临时运行态，不属于文档正文、快照或操作日志。它不得写入 MySQL `document_op_log`、Redis 的正文 pending log、MinIO Snapshot 或 Elasticsearch；服务重启、Session 离开或 TTL 到期后允许消失。

当前阶段后端按**单实例**运行。跨实例实时中继不在本阶段实现；若未来部署多个文档 WebSocket 实例，CRDT Update 与 Awareness 必须一起补齐中继，不能只中继光标。

## 2. Awareness 状态模型

前端对外使用以下状态语义：

```text
Awareness State
├─ user
│  ├─ userId
│  ├─ name
│  ├─ color
│  └─ sessionId
│
├─ cursor
│  ├─ anchor
│  └─ head
│
└─ agent
   ├─ operationId
   ├─ status: reading / thinking / editing / idle
   └─ workingRange
      ├─ from
      └─ to
```

### 2.1 user

`user` 表示该 Awareness 状态的认证主体和连接会话：

- `userId`：认证用户 ID；
- `name`：第一版使用认证主体中的 `username`；
- `color`：服务端按活跃 Session 分配的光标颜色；
- `sessionId`：服务端 WebSocket Session ID，用于区分同一用户打开的多个窗口。

同一用户的多个窗口属于不同 Session，因此应显示不同的 Session 标识，也应使用不同的光标颜色。Session 重连后会得到新的服务端 Session ID 与可能不同的颜色；这符合“连接会话”而非“用户资料”的第一版语义。

### 2.2 cursor 与文本框选

Tiptap/y-prosemirror 的协作光标机制使用 `cursor.anchor` 和 `cursor.head` 两个 Yjs Relative Position：

- `anchor == head`：表示普通光标；
- `anchor != head`：表示文本框选范围。

因此不再额外维护 `selection.fromRelativePosition` 与 `selection.toRelativePosition`。选区是 `cursor` 的派生语义，维护两份位置会产生不一致风险。

位置必须使用 Yjs Relative Position，不能使用普通文本 offset。并发编辑发生插入、删除后，相对位置才能继续映射到同一语义位置。

### 2.3 agent

`agent` 是应用扩展状态：

- `operationId`：一次协作 Agent 操作的唯一标识；
- `status`：`reading`、`thinking`、`editing` 或 `idle`；
- `workingRange`：Agent 正在读取或编辑的相对位置范围。

该字段只同步状态和范围，禁止放入提示词、思考过程、模型原始输出或其他敏感、高频内容。若 Agent 由浏览器会话驱动，复用当前 Awareness 通道即可；若 Agent 在服务端异步运行，需要后续设计代表用户加入文档协作通道的内部身份与连接机制。

## 3. 后端职责

后端不解析 Yjs Relative Position、光标、选区或 Agent 工作范围，只透明转发 Awareness 二进制 payload。后端负责认证绑定、Session 元数据、颜色分配、加入回放和退出清理。

### 3.1 Session 元数据

客户端 `JOIN_DOCUMENT` 必须附带 `awarenessClientId`，即当前 `Y.Doc` 的 client ID。后端据此建立：

```text
WebSocket sessionId
  ↔ awarenessClientId
  ↔ userId / username
  ↔ cursorColor
```

原因是后端 WebSocket Session ID 与 Yjs Awareness client ID 不同：前者用于服务端连接管理，后者用于前端调用 `removeAwarenessStates` 清理远端光标。

服务端复用既有、但此前未启用的 `AWARENESS_META` 控制帧下发可信元数据。客户端不得自行决定远端展示的 `userId`、名称、Session ID 或颜色。

建议的控制帧语义：

```json
{
  "protocolVersion": 1,
  "type": "AWARENESS_META",
  "action": "UPSERT",
  "documentId": 123,
  "awarenessClientId": 123456789,
  "sessionId": "server-websocket-session-id",
  "userId": 42,
  "name": "alice",
  "color": "#3B82F6"
}
```

`action` 还支持 `REMOVE`。`REMOVE` 至少包含 `documentId`、`awarenessClientId` 与 `sessionId`。

### 3.2 按 Session 分配颜色

颜色不再按 `userId` 持久化，也不能仅由 `sessionId` 哈希直接计算：简单哈希可能发生颜色冲突或得到视觉上过于接近的颜色。

单实例 Room 内应维护已占用颜色：

1. 以 `sessionId` 作为颜色选择种子；
2. 从固定的高对比色板选择起始位置；
3. 若颜色已被本 Room 其他活跃 Session 占用，则继续探测下一候选色；
4. 将最终颜色保存到 `DocumentSessionContext`；
5. Session 离开时释放该颜色。

这样可以保证同一活跃 Room 内不同 Session 使用不同颜色。颜色只存在于 JVM 内存，不需要新建数据库表或 Redis 持久化结构。

### 3.3 Awareness 接收、缓存与加入回放

每个活跃 `DocumentSessionContext` 需要保存该 Session 最新一帧 awareness payload。该缓存只保留最新值，不保存历史。

处理顺序：

1. JOIN 成功后，服务端为新 Session 分配颜色并建立元数据；
2. 向新 Session 下发现有协作者的 `AWARENESS_META`；
3. 向新 Session 回放这些协作者最新的 awareness payload；
4. 向既有协作者广播新 Session 的 `AWARENESS_META UPSERT`；
5. 新 Session 首次发送 awareness 后，服务端缓存并转发该 payload。

没有回放缓存时，新加入者必须等待其他用户移动光标或下一次 awareness 心跳，才能看到已有光标，因此该缓存是必需运行态。

### 3.4 退出与幽灵光标清理

以下所有路径必须收敛到同一个 Session 清理方法：

- 客户端 `LEAVE_DOCUMENT`；
- WebSocket 正常关闭；
- 传输异常；
- 慢客户端或发送失败导致的关闭。

清理步骤：

1. 捕获该 Session 的 `awarenessClientId`、`sessionId` 与 Room 上下文；
2. 删除其最新 awareness 缓存并释放颜色；
3. 从 Room 移除 Session；
4. 向其他活跃 Session 广播 `AWARENESS_META REMOVE`；
5. 前端收到后立即按 `awarenessClientId` 调用 `removeAwarenessStates`。

不能只依赖 Awareness 的自然超时清理，否则远端光标可能残留约 30 秒。`DocumentRoom` 内部发送失败时若自行移除 Session，也必须触发同一清理流程，避免 presence、颜色和光标状态脱节。

### 3.5 帧大小与频率

本阶段不新增、不修改文档模块配置项：

- `AWARENESS` 二进制帧复用现有 `jacolp.document.websocket.max-update-bytes` 上限；
- `AWARENESS_META` 继续使用当前 WebSocket 容器的文本帧限制；
- 不为 `agent.workingRange` 单独增加更大的上限。

后端仍应拒绝空或超限的 Awareness payload；前端后续应对高频光标移动做节流，避免无意义地占用出站队列。

## 4. 当前权限边界

当前文档仍采用个人模式：`teamId = owner_user_id`，只有文档所有者可以 JOIN。上述后端能力可以完整支持同一用户打开多个窗口时的光标、框选和 Session 区分。

不同账号同时协作同一文档仍依赖后续的文档分享、成员关系或团队 ACL；本阶段不改变该授权边界。
