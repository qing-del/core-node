# 文档模块重构 v0.4｜文档级用户授权设计

> **状态**：设计基线，待实现。  
> **目标**：将 v0.3 的“个人文档域（`team_id == ownerUserId`）”升级为“文档所有者 + 直接用户授权”的协作模型。  
> **范围**：只改 document 模块的资源级访问控制；OAuth scope、Yjs 二进制传输、Redis / MySQL / MinIO 的持久化职责保持既有边界。

## 1. 背景与改动目标

v0.3 中，`biz_document.team_id` 的实际含义是文档所有者用户 ID。所有 HTTP 查询、WebSocket JOIN、Room 运行态和 Redis Room Meta 都以“`team_id` 必须等于当前用户 ID”为访问条件。因此文档只能由创建者访问，无法支持对其他用户的读写授权。

v0.4 改为以下模型：

1. 每篇文档有且只有一个所有者。
2. 所有者可以向指定用户授予 `READ` 或 `WRITE` 权限，也可以撤销已有授权。
3. 授权只作用于该篇文档，不改变用户的全局 OAuth scope。
4. `WRITE` 包含 `READ`；普通协作者不能转授权、删除文档或变更所有者。
5. 读者可通过 WebSocket 同步和接收实时更新，但不能发送 CRDT 更新；写者可编辑正文。

## 2. 权限模型

### 2.1 有效权限

调用方对某篇活跃文档的有效权限按以下顺序判定：

1. `document.owner_user_id == currentUserId`：`OWNER`，拥有全部文档操作权限。
2. 存在一条 `biz_document_user` 记录，且 `user_id == currentUserId`、`enabled = 1`：按其 `permission` 返回 `READ` 或 `WRITE`。
3. 其他情况：无权访问。对外统一返回“文档不存在或无权访问”，不泄露文档是否存在。

`OWNER` 不是 `biz_document_user.permission` 的普通取值。所有者身份必须来自文档本身，避免协作者通过一条可编辑的授权记录获得管理权限。

### 2.2 操作矩阵

| 操作 | OWNER | READ | WRITE |
| --- | :---: | :---: | :---: |
| 列出可见文档、读取元数据 | 是 | 是 | 是 |
| WebSocket JOIN、Bootstrap、接收实时更新 | 是 | 是 | 是 |
| 发送 awareness | 是 | 是 | 是 |
| 发送 `CLIENT_UPDATE`、修改 Yjs 正文 | 是 | 否 | 是 |
| 修改标题 | 是 | 否 | 否 |
| 删除文档 | 是 | 否 | 否 |
| 新增、修改、撤销用户授权 | 是 | 否 | 否 |

本版将标题、删除和授权管理视为“文档管理”操作，不默认赋予写者。若后续产品需要协作者改标题，应新增独立权限位，而不是隐式扩大 `WRITE` 的语义。

### 2.3 OAuth scope 与资源 ACL 的关系

现有 `document:read` / `document:write` scope 继续作为**路由级能力门槛**：它决定用户是否可调用相应文档能力。`biz_document_user` 是**资源级 ACL**：它决定用户是否能操作某一个 `documentId`。

不能把单篇文档的授权写入 JWT scope。JWT 有效期内授权撤销无法即时生效，且 scope 数量会随文档数量增长。服务端必须在访问资源时查询或读取可失效缓存的 ACL。

## 3. 数据模型

### 3.1 `biz_document`

将现有 `team_id` 更名为 `owner_user_id`，明确其为所有者而非团队域：

```sql
ALTER TABLE `biz_document`
    ADD COLUMN `owner_user_id` bigint NULL COMMENT '文档所有者用户ID' AFTER `id`;

UPDATE `biz_document`
SET `owner_user_id` = `team_id`
WHERE `owner_user_id` IS NULL;

ALTER TABLE `biz_document`
    MODIFY COLUMN `owner_user_id` bigint NOT NULL COMMENT '文档所有者用户ID',
    ADD KEY `idx_document_owner_deleted_time` (`owner_user_id`, `deleted`, `last_modify_time`);
```

生产迁移必须先以新增列、回填、双读或兼容部署的方式上线；确认全部实例使用 `owner_user_id` 后，才在后续迁移中删除 `team_id` 和旧索引。不得在同一次发布中直接删除旧列。

### 3.2 `biz_document_user`

新增文档与用户的直接授权表：

```sql
CREATE TABLE `biz_document_user` (
    `document_id` bigint      NOT NULL COMMENT '关联 biz_document.id',
    `user_id`     bigint      NOT NULL COMMENT '被授权用户ID',
    `permission`  varchar(16) NOT NULL COMMENT 'READ 或 WRITE；WRITE 隐含 READ',
    `enabled`     tinyint     NOT NULL DEFAULT 1 COMMENT '授权是否生效(0:已撤销,1:生效)',
    `create_time` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    `update_time` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                                 ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (`document_id`, `user_id`),
    KEY `idx_document_user_visible` (`user_id`, `enabled`, `document_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='协作文档用户直接授权';
```

实现中将 `permission` 映射为 Java `enum DocumentPermission { READ, WRITE }`，并在应用层严格校验。`WRITE` 表示“可读可写”，不存储字符串 `"read,write"`：后者语义重复，无法获得可靠的数据库约束，也会增加查询和扩展复杂度。

`enabled` 仅表示授权是否有效，用于撤销后保留记录并支持再次授权时更新原行；它不是文档删除标记。文档软删除仍由 `biz_document.deleted` 表示，所有 ACL 查询必须同时过滤 `biz_document.deleted = 0`。

若后续需要审计“谁在何时授予/撤销”，可在该表补充 `grantor_user_id`、`revoker_user_id`，或新增不可变的 `document_permission_audit` 日志表；v0.4 的基本可行版本不以此为阻塞条件。

## 4. 后端实现方案

### 4.1 统一授权服务

新增 `DocumentAccessService`，作为 HTTP、WebSocket 和后台流程的统一入口。它至少提供：

```java
DocumentAccess requireRead(long documentId, long userId);
DocumentAccess requireWrite(long documentId, long userId);
DocumentAccess requireOwner(long documentId, long userId);
List<DocumentMetadata> listVisible(long userId);
```

`DocumentAccess` 应包含 `DocumentDO`、有效权限和 `owner` 标识。业务代码不得再以 `teamId == userId` 自行判断权限，避免 HTTP 与 WebSocket 的判定规则逐步漂移。

查询可采用 `EXISTS` 或两段 `UNION ALL`：一段按 `owner_user_id` 查自己创建的文档，一段从 `biz_document_user` 查有效授权文档。两段均需过滤文档软删除；写入前的授权查询必须以当前数据库状态为准。

### 4.2 HTTP 元数据与授权管理接口

现有创建接口创建时写入 `owner_user_id = BaseContext.getCurrentId()`，客户端不能传入所有者。现有列表、元数据读取改为调用 `requireRead` 或 `listVisible`；标题更新和删除改为调用 `requireOwner`。

建议新增以下接口，具体请求体名称沿用项目 Controller / Request DTO 规范：

| 接口 | 路由级 scope | 资源级要求 | 用途 |
| --- | --- | --- | --- |
| `GET /user/document/{documentId}/users` | `document:read` | OWNER | 查看授权名单 |
| `PUT /user/document/{documentId}/users/{userId}` | `document:write` | OWNER | 新增或更新为 `READ` / `WRITE` |
| `DELETE /user/document/{documentId}/users/{userId}` | `document:write` | OWNER | 撤销授权（将 `enabled` 置为 0） |

禁止所有者对自己创建普通授权记录，也禁止通过该接口转移所有权。对不存在用户、禁用用户或所有者自身的授权请求，应返回明确业务错误；对非所有者访问统一返回“无权访问”。

`DocumentMetadata` 不再返回 `teamId`。建议改为返回 `ownerUserId`（若前端确有展示需求）、当前调用方的 `permission` 和 `owner`，让前端能可靠切换只读与可编辑状态。

### 4.3 WebSocket 协作链路

这是 v0.4 的核心改造。现有 WebSocket 在握手时要求 `document:write`，且 Room 只允许 `principal.userId == teamId`。两者都只支持单人个人域。

改造步骤：

1. 握手允许持有 `document:read` 或 `document:write` 的 `user` client；仅完成 JWT 身份和全局 scope 校验，不能在握手阶段判断具体文档权限。
2. 收到 `JOIN_DOCUMENT` 后调用 `DocumentAccessService.requireRead(documentId, userId)`；通过后再创建或加入 Room，并基于该次访问创建 `DocumentSessionContext`。
3. `DocumentSessionContext` 保存 `DocumentPermission` 或 `canWrite`，而不是只保存用户 ID。
4. `CLIENT_UPDATE` 到达时必须验证写权限。为保证撤销生效，至少在每次接受更新前重新执行 `requireWrite`；可在后续优化为带版本/事件失效的短缓存，但不能无限期信任 JOIN 时的结果。
5. `DocumentRoom` 只按 `documentId` 聚合会话，不再把“所有者 ID”等同于 Room 的唯一访问域。Room 中允许同时存在 owner、读者和写者。
6. Bootstrap 读取文档时不再使用 `selectActiveByIdAndTeamId`；授权在 JOIN 阶段完成后，可通过已验证的 `DocumentDO` 或按主键读取活跃文档完成恢复。
7. 授权被撤销时，发布文档授权变更事件并由所有实例关闭该用户在对应文档的活动会话；即使关闭存在传播延迟，写入前重新授权检查仍是最终安全边界。

只读会话可以接收 Yjs bootstrap 和远端 `CRDT_UPDATE`，但前端必须禁止本地编辑器产生 Yjs update。服务端仍要拒绝恶意客户端发来的 `CLIENT_UPDATE`，前端只读不是安全控制。

### 4.4 Redis Room Meta 与生命周期

Redis Room Meta 中原有 `teamId` 仅用于验证个人域一致性。v0.4 可将其改名为 `ownerUserId`，用于记录文档归属和审计，但不得再用于判断加入者是否有权访问。Room 关闭、presence、刷盘、快照和操作日志仍只以 `documentId` 为聚合键，不受授权表变化影响。

## 5. 前端实现方案

1. 文档列表展示“我创建的”和“与我共享的”文档；可用 `owner` 或 `permission` 增加来源/只读标识。
2. 编辑路由从仅要求 `document:write` 改为允许 `document:read` 进入。新建文档入口仍要求 `document:write`。
3. 加载元数据后，根据服务端返回的有效权限决定 `editor.setEditable(canWrite)`，工具栏、标题输入框和修改操作同步禁用。
4. 只读用户依然建立 WebSocket 连接以获取 bootstrap、实时内容和 awareness；客户端不发送本地 Yjs update。
5. 所有者页面增加协作者管理入口：选择用户、授予读/写、变更权限、撤销授权。接口返回后刷新授权名单；被撤销者收到连接关闭或 `DOCUMENT_FORBIDDEN` 后回到只读不可用页。

前端状态只用于体验，不能替代服务端鉴权。尤其是写权限变化、令牌续期和多标签页场景，最终以服务端每次请求和 WebSocket 更新验证为准。

## 6. 上线与迁移顺序

1. 新增 `owner_user_id`、回填已有 `team_id`，创建 `biz_document_user` 与必要索引；此阶段不删除旧字段。
2. 先发布后端兼容版本：读取新 `owner_user_id`，已有文档所有者自动视作 `OWNER`；尚未共享的文档行为与 v0.3 完全一致。
3. 发布 `DocumentAccessService`、Mapper 改造、授权管理接口和 WebSocket 权限改造。
4. 发布前端共享列表、只读编辑态和协作者管理界面。
5. 执行数据校验与灰度验证后，删除 `team_id`、`selectActiveByIdAndTeamId` 等旧模型代码和旧索引。

迁移脚本应放入 `static/database/migrations/`，并扩展现有 migration script 测试，校验新表、索引、`owner_user_id` 回填和旧字段退役顺序。

## 7. 验收与测试

至少覆盖以下场景：

- 所有者能创建、读取、编辑、改标题、删除、授权和撤销。
- `READ` 用户能出现在列表中、能读取元数据与 WebSocket bootstrap，但发送 `CLIENT_UPDATE` 被拒绝。
- `WRITE` 用户能接收与提交 Yjs 更新，但不能改标题、删除或修改授权。
- 非授权用户无法通过 HTTP 或 WebSocket 判断文档是否存在。
- 授权升级、降级和撤销对新 JOIN 立即生效；撤销后的活动写会话不能继续持久化更新。
- 文档软删除后，所有者和协作者都不能再访问；保留的授权记录不会使文档重新可见。
- 多实例环境下，授权撤销事件会关闭目标协作者会话；即使事件延迟，写入前权限复核仍可阻止后续更新。
- MyBatis 映射、授权服务、WebSocket Handler、前端只读态与数据库迁移均有回归测试。

## 8. 非目标

- 不实现公开链接、匿名访问、邀请码或组织/团队级继承授权。
- 不改变 Yjs 数据格式、Snapshot 合并逻辑、`document_op_log` 幂等策略或对象存储路径。
- 不把文档 ACL 扩展到旧笔记、媒体、音频等模块。
- 不在 v0.4 中实现所有权转移；该能力需要额外的审计、确认和并发语义设计。

## 9. v0.4 补充说明｜短链分享授权扩展

### 9.1 与原始 v0.4 范围的关系

第 8 节的“非目标”针对原始 v0.4 设计基线：原始范围只包含所有者与指定用户之间的直接 `biz_document_user` ACL，不包含公开链接、匿名访问或邀请码。本节是后续的短链分享授权扩展，不删除或改写原始历史设计。

新增能力的准确语义是：**链接可以被转发，但分享链接本身不是匿名访问凭证；兑换前必须登录**。它不改变 OAuth 全局 scope，也不创建第二套文档权限模型。

### 9.2 权限与安全边界

1. 所有者仍由 `biz_document.owner_user_id` 判定，只有所有者可以创建、查询和撤销自己生成的分享短链。
2. 普通协作者只有其现有文档级 `READ` / `WRITE` 能力，不能管理分享短链、转移所有权或通过短链扩大自己的文档管理权限。
3. 分享链接兑换者必须使用已登录的 `user` client；`admin` client、匿名请求和无效认证上下文都不能兑换。
4. `READ` 分享只产生 `READ` 资源 ACL；兑换者还必须具有全局 `document:read` 或 `document:write` scope。
5. `WRITE` 分享只能由具有全局 `document:write` scope 的 `user` client 兑换。短链不能提升 OAuth scope，不能把只有 `document:read` 的用户变成写者。
6. 兑换成功后写入现有 `biz_document_user`，后续 HTTP 元数据访问、Yjs WebSocket JOIN、正文更新和撤销都继续使用现有 `DocumentAccessService` / ACL / WebSocket 安全边界。
7. 既有直接 ACL 的更高权限不会被 `READ` 分享降级；短链撤销只阻止未来兑换，不自动删除已经产生的直接 ACL。ACL 被所有者撤销后，重复兑换不会借台账重新复活权限。

### 9.3 短链生命周期接口

| 接口 | 调用者 | 作用 |
| --- | --- | --- |
| `POST /user/document/{documentId}/share-links` | `user` + `document:write` + 资源 OWNER | 创建带权限、有效期和最大兑换次数的短链 |
| `GET /user/document/{documentId}/share-links` | `user` + `document:read` + 资源 OWNER | 查询本人生成的短链状态，不返回原始 token |
| `DELETE /user/document/{documentId}/share-links/{shareLinkId}` | `user` + `document:write` + 资源 OWNER | 软撤销本人生成的短链 |
| `GET /s/{code}` | 未认证也可导航 | 只返回前端分享页的临时 302，不查库、不兑换、不增加次数 |
| `POST /user/document/share-links/{code}/redeem` | 已认证 `user` + 文档 scope | 校验短链、scope、文档和限次后写入现有 ACL |

创建响应中的 `shareUrl` 是原始短链 URL 的唯一返回时机；后端只保存 token hash，历史查询响应中的 `shareUrl` 为 `null`。前端不得尝试从 `shareLinkId`、文档 ID 或其他状态重建 token。

兑换服务对同一“分享短链 + 用户”使用兑换台账保证幂等：重复兑换不重复写 ACL，也不重复消耗 `used_count`。未兑换成功的请求不会消耗次数；链接过期、已撤销、已耗尽、文档已删除、账号停用、scope 不足或权限已撤销时都不能进入文档。

### 9.4 客户端访问与登录回跳流程

完整流程如下，文档 ID 只接受 redeem 响应返回的值，不能从 code 解码或推断：

```text
/s/{code}
    │  后端 GET，仅 302，不兑换
    ▼
/share/documents/{code}
    │
    ├─ 未登录 ──► /login?redirect=/share/documents/{code}
    │                 │
    │                 └─ user 密码/邮箱验证码登录成功
    │                       └─ router.replace 回到分享页
    │
    └─ 已登录 user + 文档 scope
                      │
                      └─ POST /user/document/share-links/{code}/redeem
                            │
                            └─ 使用响应 documentId
                                  └─ router.replace /user/documents/{documentId}
```

分享页只展示“正在验证分享链接”“正在获取文档权限”等状态和中性失败提示，不在页面、toast、日志或异常文本中输出完整 code。成功跳转使用 `router.replace`，避免带 code 的分享页成为成功后的历史入口。登录回跳只允许本站精确的 `/share/documents/{43 位 Base64URL code}` 路径，拒绝绝对 URL、协议相对 URL、其他路由、query 和 fragment，防止开放重定向。

前端只读/可编辑状态仍由文档元数据与现有协作客户端决定。兑换响应的 `permission` 不能替代元数据读取，不能伪造 metadata，不能绕过 Yjs WebSocket 的 JOIN、写入前权限复核或服务端 ACL 判定。

### 9.5 Vite 开发环境的跳转管理

开发环境中，Vite 只代理后端拥有的路径；前端分享落地页仍由 SPA 处理：

```ts
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      rewrite: path => path.replace(/^\/api/, '')
    },
    '/ws': {
      target: 'ws://localhost:8080',
      ws: true
    },
    '/s/': {
      target: 'http://localhost:8080'
      // 不 rewrite；后端必须收到原始 /s/{code}
    }
  }
}
```

`/api/` 继续代理 HTTP API，`/ws/` 继续代理 WebSocket，`/s/{code}` 代理到后端短链跳转控制器；`/share/documents/:code` 不进入 proxy，由 Vite 的 SPA fallback 返回前端应用。`/s/` 不能被改写为 `/share/`，也不能由 SPA fallback 直接吞掉。

### 9.6 Nginx 生产环境的跳转管理

生产站点必须让短链 location 在通用 SPA fallback 逻辑上优先匹配：

```nginx
location ^~ /s/ {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header CF-Connecting-IP $http_cf_connecting_ip;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $host;
    proxy_intercept_errors off;
    access_log off;
}

location ^~ /api/ {
    # 保持现有 /api/ rewrite 和后端代理配置
}

location / {
    # 静态站点 + try_files $uri $uri/ /index.html;
    # /share/ 不单独代理，继续由 SPA fallback 处理
}
```

`location ^~ /s/` 必须将原始路径转发给 `http://backend`，保留 `Host`、真实 IP 和 `Forwarded` 相关请求头，并透传后端 302；`/api/`、`/ws/`、`/active/`、`/common/` 的既有行为不变。不要把 `/share/` 代理到后端，否则前端分享页不会被 SPA 接管。

由于兑换接口的 code 也位于 URL path，Nginx 还应为 `/api/user/document/share-links/` 配置更具体的同目标代理，并关闭该窄路径的 `access_log`；该 location 必须保留通用 `/api/` 的 rewrite、请求头和后端目标，避免已认证兑换请求把凭证写入访问日志。

### 9.7 `jacolp.app.base-url` 配置

`jacolp.app.base-url` 必须是用户实际访问前端的公开 origin，因为后端会以它生成 `{base-url}/s/{code}`：

| 场景 | 配置示例 |
| --- | --- |
| Vite 开发服务器 | `http://localhost:5173` |
| 本地 Nginx + Docker | `http://localhost` |
| 生产部署 | `https://app.example.com` |

开发配置位于 `middleware-server/src/main/resources/application-dev.yml`；Docker 通过 `JACOLP_APP_BASE_URL` 注入，默认值对应本地 Nginx。生产环境必须改为真实公开域名，不能写 `backend:8080`、容器内部地址或只对后端可达的 `localhost`。错误配置会让用户拿到指向 `localhost` 或内部服务的不可用分享链接。

### 9.8 额外安全约束

- code 只作为 URL path 的不透明值使用，客户端调用 API 时先做 Base64URL 形状校验并使用 `encodeURIComponent`；不能拼接 document ID。
- code、原始 `shareUrl` 和包含它们的错误信息不得写入 localStorage、cookie、日志或遥测；组件卸载/关闭分享弹窗时清理内存中的一次性展示值。
- `/s/{code}` 使用临时 302、`Cache-Control: no-store` 和 `Referrer-Policy: no-referrer`；它只是导航入口，不是授权入口。
- 短链撤销、过期、耗尽、重复兑换和 ACL 撤销的最终判定均在后端事务与数据库状态中完成，客户端校验只用于体验和 fail-closed 展示。
