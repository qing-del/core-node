# 文档模块 v0.7｜后端运行说明

本文只描述 v0.7 后端能力的配置和发布顺序；前端节点属性兼容留待后续阶段处理。配置示例位于
`../../../middleware-server/src/main/resources/application.example`，本地开发 profile 位于
`middleware-server/src/main/resources/application-dev.yml`。

## 默认状态

以下开关默认关闭，普通启动不会连接 Canal、清空或写入 `file` 投影，也不会执行历史节点迁移：

| 配置 | 默认值 | 作用 |
| --- | --- | --- |
| `jacolp.document.file-index.enabled` | `false` | 装配 `file` mapping、投影消费者和补全接口 |
| `jacolp.document.file-index.rebuild-on-start` | `false` | 启动时执行一次可重复的全量重建 |
| `jacolp.document.file-index.canal.enabled` | `false` | 启动 Canal Java Client 增量监听 |
| `jacolp.document.node-migration.run-on-start` | `false` | 启动时执行一次历史节点身份迁移 |

`rebuild-on-start=true` 必须与 `file-index.enabled=true` 一起使用。全量重建完成后应立即将
`rebuild-on-start` 改回 `false`，避免下一次重启再次清空并重建投影。

## 关键配置

```yaml
jacolp:
  elasticsearch:
    index:
      file: file
  document:
    file-index:
      enabled: false
      rebuild-on-start: false
      canal:
        enabled: false
        host: 127.0.0.1
        port: 11111
        destination: example
        filter: personal_saas[.].*
        batch-size: 100
        poll-delay-ms: 100
    node-migration:
      run-on-start: false
      page-size: 100
      max-update-batch-bytes: 524288
      max-cas-retries: 3
```

`max-update-batch-bytes` 是 Java 调用 Yjs 身份迁移接口时的请求批次软上限，不能超过 Yjs 服务当前
16 MiB 请求体限制；默认 512 KiB。`file` 是逻辑索引名，实际物理名称由
`jacolp.elasticsearch.index.file` 决定。

Canal 的默认连接参数与 `../../dataCentre/canal-java-client-config.md` 一致：destination 为
`example`、TCP 端口为 `11111`、订阅过滤为 `personal_saas[.].*`。Java 应用在 `dev-net` 内运行时
使用 `host=canal`；在宿主机运行时使用 Canal 所在机器的地址。使用
`static/dataCentre/docker-compose.yml` 时，请确认 MySQL 数据库名与应用及 Canal 过滤规则一致，
即使用 `personal_saas`。

## 发布顺序

1. 确认 MySQL、Redis、RabbitMQ、Elasticsearch 和 Canal 可用，并确认没有活跃文档协作会话。
2. 配置 `jacolp.elasticsearch.index.file`，设置 `file-index.enabled=true`，启动一次以创建 mapping。
   mapping 初始化只创建索引，不写入业务数据。
3. 在维护窗口设置 `rebuild-on-start=true`，启动应用完成全量重建；检查 NOTE、IMAGE、DOCUMENT
   及软删除文档，随后关闭该开关并重启或重新发布配置。
4. 校验稳定 `_id`（例如 `NOTE:1`、`IMAGE:1`、`DOCUMENT:1`）和 `visibleUserIds` 后，开启
   `file-index.canal.enabled=true`。Canal 发布 RabbitMQ 成功后才确认 batch，消费者会重新读取
   MySQL 当前事实状态构建投影。
5. 确认 `GET /user/file/completion` 的认证 token 带有需要的 `note:read`、`media:read` 或
   `document:read` scope 后，再对外启用补全接口。
6. 单独安排历史迁移窗口，设置 `node-migration.run-on-start=true` 启动一次；观察结构化日志中的
   `documentId`、节点路径、成功/跳过/CAS 冲突/失败原因，完成后关闭该开关。

## 失败恢复

- 全量重建失败时，修复事实源或 ES 连接后可重复执行；任务会先清理当前 `file` 投影，硬删除资源不会
  被重新写入，软删除资源仍保留为 `isDelete=true`。
- Canal 发布失败会 rollback 当前 Canal batch；ES 投影失败沿用现有 RabbitMQ retry/DLQ。重复事件使用
  稳定 `_id`，不会产生重复资源文档。
- 节点迁移失败不会写入迁移状态表。修复原因后可重复执行；已有 `nodeId`/`nodeVersion` 不会被覆盖，
  CAS 失败的未引用快照会被尽力清理，Redis pending updates 不由迁移任务删除。

## 验收重点

- 修改 NOTE/IMAGE 名称、公开状态、软删除状态和 IMAGE URL 后，确认对应 `file` 文档刷新。
- 修改文档用户的 READ/WRITE、enabled 状态后，确认 `visibleUserIds` 刷新；owner 始终存在。
- 使用不同 token scope 调用补全接口，确认缺少某类 read scope 时 ES 查询显式排除该 `resourceType`，
  且返回不包含 `visibleUserIds` 和 `isDelete`。
- 重放同一资源事件，确认稳定 `_id` 下结果仍只有一份；重启后确认历史迁移不会重新生成已有节点身份。
